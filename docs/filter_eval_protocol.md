# 过滤评测协议（filter_eval_protocol）

> 四层指标，每层都要"可算、可复现、可写进论文表"。
> 实现：`code/eval_filter.py` → `outputs/reports/filter_eval.md` + `.json`

## 一、评测数据

- **主评测集**：`4_Synthetic_Mixtures` 的 test split（500 条，训练期不可见）。
- **补充评测集**：真实 demo 音频 `outputs/audio/*.wav`（10 条已知类别，人工标注），用于检验合成-真实的域间隙。
- **主观评测**：≥5 人 AB 偏好测试，素材为 10 条真实音频过滤前后各 1 次播放（盲听，随机顺序）。

## 二、第 1 层：检测层（上游依赖，已知不达标）

| 指标 | 定义 | 现状（fold 9, τ=0.5） | 目标 |
|---|---|---:|---:|
| 事件召回（核心 3 类） | 一个事件任一窗命中即算 | 83.3% | ≥ 95% |
| 误报率 | 每事件 / 每小时误报数 | 123.8 次/h | ≤ 5 次·h⁻¹ |
| 段级准确率 | 10 类 top-1 | 64.11% | ≥ 85% |

> **门控级过滤的启用条件**：事件召回 ≥ 95% **且** 误报 ≤ 5 次·h⁻¹。在此之前只允许「增益级过滤 + fail-open」，报告中必须并列这一事实。

## 三、第 2 层：过滤层（核心，本次交付）

| 指标 | 公式 | 目标 |
|---|---|---|
| **目标抑制量** `Supp_dB` | `10·log10( Σ‖s_t‖² / Σ‖ŝ_t‖² )`，`ŝ_t` = 同一掩码施加于 target stem 后的输出 | ≥ 12 dB（A）/ ≥ 20 dB（B） |
| **白名单保留率** `Pres_dB` | `10·log10( Σ‖ŝ_i‖² / Σ‖s_i‖² )`（interferer stem 施加同一掩码） | ≥ −1 dB（即衰减不超过 1 dB） |
| **静默压制率** | 白名单 stem 被衰减 > 3 dB 的样本占比 | **0%** |
| **类间泄漏** | 抑制目标时对白名单造成的额外损失（`Pres_dB` 相对基线 − 目标抑制量） | ≤ 3 dB |
| **SDR 提升** | `SI-SDR(ŷ, s_keep) − SI-SDR(y, s_keep)`，`s_keep = interferer + noise` | > +5 dB |
| **PESQ** | 对 `s_keep` 参考的 PESQ（若 pesq 库可用） | 相对下降 ≤ 0.2 |

### 3.1 掩码施加法（避免"评测作弊"）

不能用"过滤前/后的混音能量"直接算抑制量——因为混音的复杂度会变化。正确做法：

1. 用混音 `x` 计算掩码 `M(x)`；
2. **同一个 `M(x)`** 分别施加于 `target stem` 与 `interferer stem`；
3. 比较各自的输入/输出能量 → `Supp_dB`、`Pres_dB`。

这等价于假设掩码对分轨线性可加，是 TSE 评测的通行近似，必须在报告中声明。

## 四、第 3 层：体验层

| 指标 | 测量方法 | 目标 |
|---|---|---|
| 端到端延迟 | `t_out − t_in`，分 chunk 实测 + 归因表（特征/推理/OTA） | ≤ 100 ms |
| 实时率 RTF | 处理时长 / 音频时长 | ≤ 1.0（有实时余量） |
| CPU 占用（单核） | `psutil` 或 `time.process_time` 差值 / 墙钟 | ≤ 80% 单核 |
| 音质（非目标段） | PESQ / 段级 SNR | PESQ 下降 ≤ 0.2 |
| 主观偏好 | 5 人盲听 AB："过滤后更舒适且未漏掉警报" | ≥ 70% 偏好过滤后 |

### 4.1 主观评测问卷（固定题项）

1. 哪一段更舒适？（二选一）
2. 过滤后你是否听到警报声？（是/否/不确定）
3. 过滤后是否有不自然的抽气/呼吸声？（是/否）
4. 是否愿意在真实场景中使用？（1–5 分）

## 五、第 4 层：安全层（否决项）

| 指标 | 定义 | 判定 |
|---|---|---|
| **静默压制次数** | 白名单类被检出（p > 0.5）但输出被衰减 > 3 dB 的次数 | **必须 = 0**，否则整版不可发布 |
| fail-open 生效次数 | 触发 fail-open 的次数 / 总 chunk 数 | 报告记录（非缺陷） |
| 硬旁路响应 | 开关触发到音频直通的延迟 | ≤ 1 个 chunk（32 ms） |

## 六、报告结构（`filter_eval.md` 固定骨架）

1. 一句话结论（是否达成 4 层门槛）
2. 数据与设备（test split 规模、GPU/CPU、模型 checkpoint 哈希）
3. 逐层指标表（含与目标值的差距）
4. 方案 A vs 方案 B vs 混合（C）对照表
5. 失败案例分析（≥3 条，含音频文件名）
6. 局限与下一步（明确列出 AED 门控前提未满足）
7. 复现命令

## 七、可复现性要求

- 随机种子固定（`42`）；掩码平滑参数写入 `filter_eval.json`。
- 每条样本的指标都要落 `per_sample.csv`（500 行），便于定位异常样本。
- checkpoint 记录 `sha256` 前 12 位。
